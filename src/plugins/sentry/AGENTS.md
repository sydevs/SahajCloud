# Logging and error reporting

How a failure reaches the application log and Sentry, and what each capture site reports. What an error's response body discloses is a Payload config setting, in `docs/architecture.md`.

Server logging uses a custom console-backed logger (`src/lib/logger/workerSafeLogger.ts`). It implements the Pino subset Payload uses, respects `NEXT_PUBLIC_LOG_LEVEL`, and normalizes `Error` objects into plain serializable ones. Error tracking uses Sentry (`@sentry/nextjs`): `src/instrumentation.ts` / `src/instrumentation-client.ts` initialize it, `next.config.ts` wraps with `withSentryConfig`, and `src/app/global-error.tsx` reports React errors. Source maps upload when `SENTRY_AUTH_TOKEN` is set at build time. **The `environment` FIELD comes from the Railway environment name, never `NODE_ENV`** — the field `Sentry.init` sets on every event, which is the only place the deployment is recorded; no capture adds a tag beside it — Railway builds a preview with `NODE_ENV=production`, so reading it tagged every preview error `production` and made preview noise indistinguishable from a real incident (#733). `deploymentEnvironment()` (`@/lib/env/deploymentEnvironment`) is the one definition, shared with the storage isolation guard's `railwayEnvironmentName()`, and falls back to `NODE_ENV` off-Railway so a local run still reports `development`. The browser's one `Sentry.init` (`src/instrumentation-client.ts`) calls `clientDeploymentEnvironment()` instead, since a browser bundle reads no `process.env` at runtime: `next.config.ts`'s `env` block inlines the same name under `NEXT_PUBLIC_DEPLOYMENT_ENVIRONMENT` at build time, needing no dashboard variable (#737, mechanism in `docs/environment.md`). `ErrorBoundary`, `global-error.tsx` and `clientLogger` capture through the client that `init` installs, so the field reaches every browser event from one place (#760). `SENTRY_TRACES_SAMPLE_RATE` (default `0.1`) enables a DB-span breakdown on every admin request. `meditations.recomputeNodeWeights` and `frames.cascadeNodeChange` also carry manual spans (#529).

## A caller's mistake is not an incident (#670)

A value Postgres cannot cast (SQLSTATE `22P02`) used to surface as an unhandled 500. `@/plugins/databaseErrors` now maps it, in Payload's root `afterError` hook, to a 400 naming the bad value, and stops it reaching Sentry. Every other error class is untouched. This covers Payload's own REST routes only. A custom endpoint that catches its own errors — `src/collections/Events/endpoints/geojson.ts` is the one that does — must call `mapPostgresCastError` itself.

## A rejected credential is not anonymous traffic (#734)

The same root `afterError` hook classifies a captured sub-500 error by what its `Authorization` header did (`src/plugins/sentry/authAttempt.ts`). No header is an anonymous read and keeps today's `warning` level and default grouping. A header that authenticated is an ordinary access-control denial, also unchanged. A header present with no `req.user` means **every strategy refused the credential** — always a broken integration — so it is captured at `error`, under its own Sentry fingerprint, and mirrored to the application log at WARN so Railway alone answers it.

Attribution is the auth scheme, the collection slug, the `User-Agent`, `cf-connecting-ip`, and a 12-hex truncated SHA-256 of the key. **Never the key, or any substring of one.** The IP goes on Sentry's `user.ip_address`, the one field `sendDefaultPii: false` and the project's _Prevent Storing of IP Addresses_ setting both act on — in an `extra` it would be opaque context that no scrubber reaches and no setting turns off. Trust it only as far as the edge: a request that skips Cloudflare can set that header to anything, so the key fingerprint, not the IP, is what names an integration. The scheme comes from an allowlist, because a malformed header's first word can be the credential itself; the collection is checked against `req.payload.collections`, because it reaches a grouping fingerprint and an unchecked word would let any caller open a Sentry issue per value it invents. Grouping is by collection, not by key fingerprint, for the same reason — the fingerprint is a tag, which segments within the group.

⚠ **The `error` level is caller-triggerable, and that is accepted.** Any anonymous caller can raise a captured 400/403/404 to `error` by sending a junk `Authorization` header. Grouping is bounded by the collection check, so the cost is event quota and alert noise rather than issue sprawl. Mute it with a Sentry-side rule on the `auth_outcome` tag, not by dropping the level — the level is what distinguishes the signal.

⚠ **The hook sees only what Payload's error handler sees.** A custom endpoint that denies by _returning_ a 403 `Response` never throws, so nothing reaches the hook. `requireActiveClient` (`src/lib/endpoints/requireActiveClient.ts`) reports its own denials for that reason (#743) — one seam covering the fifteen handlers that short-circuit on it, `/api/atlas/seo` and `/api/atlas/sitemap` among them. Both paths share `src/plugins/sentry/credentialRejection.ts` — one tag set, one fingerprint shape, one log message — so that a rejected key is _intended_ to group into one Sentry issue wherever it was denied. ⚠ **Unverified against Sentry itself.** The two paths capture differently (a message here, the exception in the hook — one body sends both), and only the explicit fingerprint is meant to make that irrelevant. Confirm it with one real rejection on each path before you rely on it. A 500 is deliberately left alone: the caller's credential is not what is wrong with it.

Two differences follow from the guard denying rather than throwing. It captures a **message** (through `capture`, the plugin's one body for every report) where the hook captures the exception, since there is no exception. And it is **not gated on `NEXT_PUBLIC_SENTRY_DSN`** — `sentryPlugin` returns the config untouched without one, so the hook's WARN mirror disappears with it, while the guard's line survives a local run. Reporting there never throws, and the WARN line has its own `try` so a broken transport cannot cost the Sentry event: a telemetry failure must not turn a caller's 403 into a 500.

⚠ **Every rejection reports — there is no in-process dedupe.** These fifteen endpoints are public and the edge allows 500 req/min per (client, IP), so one stale integration can post a lot of `error` events. Route that volume with the Sentry-side rule on `auth_outcome` named above, which is the one mute for both paths. A window in this process was tried and dropped in #761: it bounded the volume, and it bought a `Map`, an expiry sweep, and a test-only reset to do it.

⚠ **`requireActiveManager` is deliberately not covered.** It guards the admin surface, where a denial is a person's stale session far more often than a broken integration, and #743's criteria name the client guard alone. Adding it is a one-line call to the same helper if the admin surface ever wants the signal.

## A swallowed admin write reaches no one (#1039)

`afterError` is invoked from `routeError` and the GraphQL handler alone, so it sees only a failure a routed request answers with. The admin also writes through the **Local API**, while a page renders or inside a server function, and those failures are caught inside `node_modules`: `DocumentView` hands the error to Payload's `logError` and returns `undefined` — the page answers 200 with the admin chrome and an empty body — and `schedulePublishHandler` returns `{ error }` to the UI. Payload logs a `ValidationError` at `info` by default, so neither leaves a line that reads as an incident, and nothing escapes the render for `onRequestError` to see. That is how #1038 — nobody could create a Page at all — stood for four months, visible only in the Railway deploy log.

Two such paths exist in this app. The **autosave create-on-open** (`payload.create` while the document view renders) needs `autosave` and no `versions.drafts.validate`, so `pages` is the only collection that reaches it. **`schedule-publish`** is reachable on `pages` and `meditations`, and fails in two places: when the admin queues it, and when its job runs later. Save, Publish and the periodic autosave are not among them: they submit to the REST API and already report.

`installLocalApiCapture` (`src/plugins/sentry/localApiCapture.ts`) wraps every Local API write on the live instance from the plugin's `onInit`, and reports through the same `captureFailure` body the hook uses — one set of exclusions, so a new site cannot re-report what `mapPostgresCastError` deliberately drops. Two properties of the write's own request keep it to writes the admin makes, and both are read off the request Payload itself built rather than inferred.

**`req.payloadAPI`.** `createPayloadRequest` stamps a routed request `REST` or `GraphQL`, and `createLocalReq` **preserves that stamp** into a nested Local API call — so a write our own hooks make while a request is in flight reads as routed, and stands down rather than reporting what `afterError` is about to report. The admin page render and every admin server function build their request through `initReq`, which goes through `createLocalReq`, so both read `local`. That is why Save, Publish and the periodic autosave report exactly as they did, and why an ordinary REST 400 still produces one event.

**An acting manager on the request.** A job, a seed and an operator script carry no user. `eventImport`'s task is the case that makes "has a user" alone wrong: it passes a `user` option with no request at all, and a refused CSV row is its normal path, reported to the uploader already — so the gate asks for the user on `req`, which that call has not got.

⚠ **`jobs.queue` is wrapped separately, and reports under its own rule.** It writes the row through `payload.db.create` unless `jobs.depth` or `jobs.runHooks` is configured, so wrapping the collection operations does not reach it — and it is half of `schedule-publish`. A queue that carries a request answers the same two gates as a write, so a job or a cron tick queuing with a userless local request stands down. `schedulePublishHandler` passes **no request at all** — only `input`, `task` and `waitUntil` — so that queue reports whenever it fails, and the acting manager comes from the queued input, where `schedulePublish` records who asked. The event is tagged with the schedule's `target` too (`pages/12`, or a global's slug), so one failing schedule is not filed under every other.

⚠ **A job that fails for good is the job runner's failure, not a write's.** The runner catches a task's throw, records it on the job row and in a log line, and tells no one — a scheduled publish that never happened, or a cleanup that stopped running, was visible only in the deploy log. `installJobCapture` (`src/plugins/sentry/jobCapture.ts`) wraps every task's `handler`, which the runner reads off the live config at run time, our tasks and Payload's own `schedulePublish` alike. A cancelled job is not reported. It reports with `capture_source: job` and tags `task` and `job_id`. A task that throws `ExpectedJobFailure` (`src/lib/jobs/expectedFailure.ts`) is reported at `warning`, not `error`: its reason is an answer already shown to whoever needs it, such as an import whose target region or own row was deleted, or a recording with no speech. A deployment's own gap, such as a missing Lemonfox key or bucket URL, is expected only outside production (`isProductionDeployment()`, Railway's name), so in production it still alerts. An outage in the same task stays a plain `Error`. It passes no request: the runner's carries the default locale, and on `/api/payload-jobs/run` the admin who triggered the run. A job's own writes carry no user, or a routed request when `/api/payload-jobs/run` started it, so the write wrapper stands down inside it either way.

**Once per job, on its final attempt.** Payload has no final-failure hook that carries the error — `onFail` gets none, and runs on every attempt — so the wrap judges the last attempt itself. The handler sees the job the runner hands it, whose `taskStatus` counts the task's prior tries. For a single-task job — every job here — the runner retries task `'1'` until those prior tries reach the task's `retries` (none by default), so that comparison is the runner's own rule for the last attempt. A task run inside a workflow is not reported: the workflow's own `retries` decide its last attempt too, which the handler cannot see, and no workflow is configured. Only `schedulePublish`'s input names a target and a person, so it alone adds a `target` tag (`pages/12`) and the scheduling manager; no other task's input reaches the tags or the user, though an error's own message is sent as it is. A manual `runByID` of a job that already failed for good runs, and reports, again. **Limits:** a failure the handler never sees goes unreported — a task answering `{ state: 'failed' }` (none does), a throw after the handler returns, a task no longer registered, and a job a crash left `processing`. ⚠ A dev HMR `reload()` swaps in a fresh config without running `onInit`, so in dev the wrap lasts until the first reload.

**Two limits, accepted.** The cancel branch of `schedulePublishHandler` is a bulk `payload.delete({ where })`, which answers a per-document failure in `result.errors` rather than throwing, so the wrapper never sees it. And a nested write that a hook catches and recovers from can still send an `error` event, when the outer write is a local request with a manager, because the wrapper cannot see the catch above it: `resolveClipParent`'s lost create race and `upsertUserByEmail`'s duplicate are the two in this repo.

⚠ **The capture reads `data.errors[].path`, not the message.** A `ValidationError`'s message carries field _labels_, which are localised and change with the editor's language. `tests/int/admin-write-capture.int.spec.ts` pins the paths, and the `REST` preservation above, against a real failed `payload.create` — nothing in this repo sets `payloadAPI`, so only a real write can show the gate still holds after a Payload bump.

**The logger was the other candidate, and it cannot name who or what.** Both swallow sites do log: `logError` calls `payload.logger[level]({ err })`, and `schedulePublishHandler` calls `payload.logger.error` directly, and `config.logger` is ours. A capture there would need no wrapper and no method list. It was not taken because the log record carries no `req`: the collection and the acting manager, which #1039's first two criteria require, are both lost. It would also need `loggingLevels: { ValidationError: 'error' }` to keep the error object at all — Payload defaults that class to `info`, which is why #1038's two log lines read as nothing happening.

The managers sign-in action and the magic-link endpoint report from their own catch (`src/components/admin/SignIn/actions.ts`, `src/plugins/login/endpoints/requestMagicLink.ts`). Their answer is uniform by design, so nothing downstream can, and they have no acting user — both are open to anyone, which is the point.
