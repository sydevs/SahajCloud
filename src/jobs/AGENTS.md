# Scheduled Jobs

Payload's `autoRun` job system runs background tasks in the same long-lived Node process on Railway — no separate workers.

⚠ **A `schedule` is dead without an `autoRun` entry for its own queue.** Payload calls `handleSchedules({ queue })` only from that queue's `autoRun` cron, so a schedule on a queue nothing ticks is never consulted — no error, no log line, no job row. The `monthly` queue was in that state from the day it was introduced until #878, so neither job on it had ever run anywhere. The pairing, and the one deliberate exception, live in `src/jobs/queues.ts`; `tests/unit/job-schedules.spec.ts` fails on the next dead schedule.

⚠ **A `payload.jobs.queue` call picks a queue the same way, and nothing drives `default`.** A row enqueued onto a queue with no `autoRun` entry — including the one an omitted `queue:` key chooses — is written for real and then waits forever, as silently as a dead schedule. The same spec reads every `jobs.queue(` call under `src/`, which is why an enqueue site names its queue with a string literal: a constant reads as no queue at all.

⚠ **A Railway PR preview has no `autoRun` at all** (`jobAutoRun()` in `src/jobs/queues.ts`). Every tick queries the database, which kept every idle preview's app and Postgres awake and billed around the clock — most of the Railway bill in Oct–Nov 2026. A queue a write kicks through `runQueueSoon` still runs there; a schedule never fires and a lost kick is never retried. To exercise a scheduled job on a preview, sign in and open `/api/payload-jobs/run?queue=<queue>`, which enqueues what is due and runs it.

- **`CleanupOrphanedMedia`** — monthly, on the `monthly` queue. It trashes newly-orphaned files/images, found via schema introspection (`schemaUtils.ts`) rather than a hardcoded list; tagged images (e.g. "featured") are preserved. Each run scans uploads created 24 hours to 3 months ago, so every upload is checked on about three runs. Phase A then permanently deletes trashed items older than `TRASH_RETENTION_DAYS` (45) **that nothing references any more**, so what one run trashes survives the next run and goes at the one after — that phase had no age check at all while the queue was dead (#878), and age was still its whole test until #1118. Both phases read one referenced-id scan, built before Phase A; a trashed item in it stays in the trash and is counted in `skippedReferenced`, because an editor may have trashed it on purpose — a count of what Phase A read while filling its delete budget, not of the backlog behind it. ⚠ The retention must stay longer than 31 days: at 30, a run after any 31-day month deleted the previous run's trash. And the scan window must stay a span, not a band chosen by `month % 3` — that is how 8 months of uploads in 12 were never scanned at all. ⚠ Review a run against real data with the `dryRun` input from the admin Jobs UI before trusting a new window or threshold: it counts and logs both phases and writes nothing.
- **`SyncLectureMetadata`** — monthly, 1st at 03:00 UTC on the `monthly` queue, whose `autoRun` ticks hourly at :07, so a run lands within the hour. Refreshes `lectures.metadata` from the Nirmala Vidya API for every `full` lecture, at up to 10 concurrent fetches with retries; a per-lecture failure is counted and the sweep continues. To run one now, queue it from the admin Jobs UI — `jobs:run --queue monthly` only drains a row already past its `waitUntil`.
- **`ExpireEvents`** — daily 02:00 UTC, single-threaded. A schedule that ran out gets `verificationStage: 'finished'` without unpublishing (#603, so an old link keeps resolving) — the public feeds filter it via `schedule.lastDate` instead. Otherwise it advances the ladder `verified → reminded → escalated → urgent → expired → trash`. Only `urgent → expired` unpublishes, and a class its manager has saved as a draft leaves the ladder altogether until it is republished (#1121). Which moves exist, and who may make each, is `EVENT_MACHINE` (`src/lib/eventVerification/machine.ts`). A stage advances only once every recipient's email is logged, so a failed send retries. Manual trigger: `pnpm payload jobs:run --queue nightly`. `EVENT_VERIFICATION_ENABLED=false` pauses the whole sweep — it returns before it queries, so nothing is sent, advanced, unpublished or trashed until it is set back.
  ⚠ **Its bookkeeping writes skip document validation** (#835). Payload re-validates the whole document on update, so an event whose _stored_ data fails a validator added after that row was written could never be advanced, finished or logged, and its reminder went out again every night. `updateEventWithoutValidation` (`src/lib/events/updateEventWithoutValidation.ts`) passes `unpublishAllLocales`, which skips validation while still writing the main row and the `latest: true` version row together. A tightened Events validator therefore no longer strands existing rows — but it also no longer stops these writes.
  ⚠ **That helper is shared, and what it excludes is the point** (#842). The `registrationsFull` sync and the community-feedback tallies write through it too: both run in unguarded `afterChange` hooks, so a refused Events write killed a visitor's registration or vote outright. **Verifying an event deliberately does not** — broken data is fixed before an event is verified, so `applyVerification` still validates, and both verify surfaces report a validation failure as one (422 from the endpoint; the failing fields, plus an edit button that signs the manager in, on the emailed verify page). A write applying editor-supplied content never comes through here either.
- **`RegistrationNotifications`** — hourly. `SendSessionReminders` reminds a registrant ~24h before their session, deduped via `activityLog`. `SendPostEventFollowUps` asks an attendee for feedback after the session.
- **`SendDigests`** — nightly 07:00 UTC on the `nightly` queue, `concurrency: { exclusive: true }` (#1070). One email per manager **per role** — program, region, admin — carrying only the sections whose own notification pace is due that morning: statistics, the open-items list, and new registrations. ⚠ **One schedule, not three.** Daily, Weekly and Monthly are decided from the run's own clock (`PACES` in `src/jobs/Digests/buildDigest.ts`), because three schedules would send three emails to one manager on a Monday the 1st. A section that is "new since" reads `(max(watermark, runStart − period), runStart]` from `Managers.digestWatermarks`, which the run advances per role and key — so a retry re-sends nothing. The nightly 06:00 tick enqueues it and the 07:00 tick runs it.
- **`RecordAtlasSnapshot`** — nightly 06:00 UTC on the `nightly` queue. One `payload.kv` key per UTC day (`atlas-snapshot:YYYY-MM-DD`), holding each region's own event counts keyed by verification stage, replaced rather than added to within a day. It is the only history a stage count has — the stage is overwritten in place on the event — so it is what a dashboard tile's "+X in 30 days" line compares against. ⚠ **A tile shows no change line at all with no snapshot that old**, never "+0": a freshly deployed environment knows nothing about 30 days ago. The task itself prunes keys older than 45 days.
- **Submission screening + retention** — `POST /api/user-submissions` (#632, #723) persists and returns immediately. `screenSubmission` reads the admin-set block on the sender's Registrant record, then runs an MX lookup, a disposable-address check, and 24h repeat-sender/duplicate-body checks, then files the row as `spam` or hands it to `deliverSubmission`. `cleanupCollections`'s `user-submissions` entry sweeps per type (`retention-submissions.int.spec.ts` holds the windows) — a 7-day floor on contact rows matters, since less would delete the history the screening checks need.
- **Submission pipeline** — the three jobs behind `user-submissions` (#724), running beside the per-collection ones above until Phase 3 deletes those. `screenSubmission` runs one uniform base for every type (disposable-address check, MX lookup, **cross-intake** sender history) plus content screening of a proposal's `proposed` patch, then queues delivery **only** on a clean verdict — which is why a refused row never reaches a recipient, a provider or a manager. `deliverSubmission` sends per type and logs every attempt, retrying only a failure that could plausibly go differently. `cleanupCollections` sweeps the per-type windows nightly at 04:00 UTC and then the `users` orphans: a sender goes with their last message unless a submission still pins them, or an admin has blocked them — a block is a decision, so the sweep never deletes the record carrying it (#630).
  ⚠ **A machine refusal is `status: 'spam'`; `rejected` is a manager's decline.** Two statuses, so abuse counting and retention both read the indexed column and neither counts a manager's judgement as a spam strike against the person who wrote in. `confirmed_spam` is an admin settling a machine refusal, and counts as a strike for the same reason `spam` does — it agrees with the machine rather than overruling it, and only an admin may set it or release the row back to `pending` (#1070). `screeningResult.verdict` says which check refused, for the reader — never whether one did. The split is also what lets retention reach a `spam` registration or subscription at 90 days while keeping every decided one for ever: a refused sign-up records neither an attendance nor a consent.
- **CSV class import** — `importEvents` on the `default` queue (#907), queued by the upload and kicked at once by `runQueueSoon`; the five-minute cron on that queue is the safety net. The job (`src/plugins/eventImport/task.ts`) geocodes every row four at a time and creates one draft class per row as the uploader, each in its own transaction; a volunteer publishes them from the import page.
- **`TranscribeRecording`** (slug `transcribeMeditation`, kept because it is a Postgres enum value) — on the `transcription` queue, whose `autoRun` ticks at :03 and every 15th minute after. Queued by `queueTranscription`, the transcript row's own `afterChange`, which also starts the queue, so the tick is only a safety net for a start that was lost. A row is created when a recording arrives: a meditation's upload, an MP3's upload to `files`, or Cloudflare Stream's `ready` webhook for a video file, whose MP4 exists only then. It reads the recording's public URL — R2 for audio, Stream's MP4 download for a video, which it waits for — asks Lemonfox for a `verbose_json` transcript with word timings, and writes subtitle-length cues (at most 30 characters, and a new cue after a 3-second pause) to the row. A meditation's language is its `locale`; a file's is detected by the run and stored, unless the row names one an editor corrected. The glossary's own spellings go as the `prompt` whenever the language is known, which is what stops the vendor writing an IAST variant (#1084). `retries: 0`, so a failure throws and the retained job row carries the message — which is where the row's virtual `status` and `error` are read from. ⚠ **It never writes the meditation** (#897, success line 12): `meditations` keeps three versions behind drafts, so a write there would burn one and could publish an editor's unfinished draft. ⚠ **It has no `concurrency` key, on purpose** — Payload holds back any job whose key matches one still marked `processing`, and a run lost to a restart keeps that flag forever, which would block a re-request after a stall for good. **Every request is this queued job.** `POST /api/meditations/:id/transcribe` (#984) and `POST /api/files/:id/transcribe` (#1016) re-request a run by replacing the row, which this task then fills; the Transcript panel's button is their only caller, and the file one also takes the corrected `language`.
- **`CleanupCollections`** — nightly, 04:00 UTC on the `nightly` queue, over every collection that declares retention inline on its own `custom.retention`, read off the built config (`@/types/retention` for the vocabulary, `src/jobs/CleanupCollections/entries.ts` for the discovery, #987). `user-submissions`, `imports` and `payload-jobs` declare one today; each config carries its windows and the reason each window is the length it is, beside the fields they age, and a collection that declares none is simply not swept. `payload-jobs` is Payload's own collection, so its declaration arrives through `jobs.jobsCollectionOverrides` (`src/collections/PayloadJobs/`) and nothing else — which is also where that collection is made visible to admins alone, since Payload ships it hidden from everyone. One task means one schedule, so the `payload-jobs` sweep moved here from a weekly cron — `JOB_RETENTION_DAYS` still bounds what goes. ⚠ **That window is the other half of `deleteJobOnComplete: false`.** A finished job row is what a meditation transcript derives its status from, so Payload may no longer drop one the moment its run ends — and nothing else bounds `payload-jobs`. It deletes a row completed, or errored with no retry left, more than `JOB_RETENTION_DAYS` (7) ago. A queued row is never swept: it is old because its `waitUntil` has not arrived, and deleting it would cancel work nobody asked to cancel. The flag is global, so this covers every queue. `transcripts` declared a window until #1043 and no longer does: a cascade from each parent takes the row before the parent goes, so no orphan reaches a sweep.
- **`RecoverLostJobs`** — hourly on the `nightly` queue (#1117). A container that dies mid-job leaves its row `processing` for ever: Payload never recovers one, and while it stands `countRunnableOrActiveJobsForQueue` stops that task's schedule queueing another. The sweep cancels every row older than `STALE_JOB_MS` (1 h, the one discriminator — running is not proof the owner died, since a rolling deploy sweeps while the old container works), then settles the documents those runs owned, which is the half cancelling alone does not do: a class import's status is written by the run, so a lost one leaves `imports` reading `pending` behind a page with no retry on it, and `failLostImports` marks it failed instead. A transcript needs nothing there — it derives its status from the job row, so the cancel is the whole recovery. ⚠ **It carries a `beforeSchedule` hook of its own**, because the sweep is the only thing that settles a lost row and a sweep lost mid-run would otherwise hold its own schedule for ever. Past `STALE_JOB_MS` such a row stops counting as active, and the run that queues is what cancels it.
- **Usage tracking** — `trackUsage` increments `dailyRequests` atomically off `afterRead`. `resetUsage` resets it daily, tracking `peakDailyRequests`. See `docs/rules/api-clients.md`.
